NormaCore Claude Controller

NormaCore Claude Controller

Implementation plan for a Python process on the Station laptop that uses the Claude API directly. Claude looks at the camera once, picks a target, and local code moves the arm. There is no MCP and no agent loop. Folder: normacore-api/

Core rule: Claude decides once, and local code does everything else. Each instruction makes exactly one Claude call with one image, and Claude's whole answer is a short list of allowed steps plus one sentence. Capture, safety checks, motion and verification all run locally with no model involved. The worst case is bounded by a hard timeout, so a 20-minute run can't happen.

Goal for the demo: the arm starts moving within a few seconds of the instruction. That's a target to check against the run log, not a measured result yet.

0. Goal

Talk to the arm in plain language, and it does what you mean. You type a request, or later say it. One Claude API call reads the request, the camera view and the arm's current joint angles, and answers with up to three allowed steps plus one sentence. Local code checks each step, sends it to the Station API, and confirms through joint feedback that the arm got there.

This proves the whole chain works: words → Claude API → checked command → Station API → motion → confirmed result. It needs no MCP and no camera–arm calibration.

1. Why the MCP run took 20 minutes, and how this design avoids it

What made it slowWhat this design does instead
The model chose every small step itself (take a photo, look, move, check, look again), and each step was a full round trip.Claude is called once per instruction. Taking the photo, moving and checking are ordinary local functions.
The conversation grew with every step and kept re-sending earlier images, so each turn got slower.Every instruction starts a fresh, short request with one cropped image.
Claude produced motion details such as joints and coordinates, so mistakes led to retries.Claude only picks from a short list of allowed steps: gestures, taught poses and small joint nudges. Local code supplies the joint values and keeps them within limits.
Nothing put a limit on total time.There's a hard timeout of about 8 s. When it runs out, the arm declines and stays put.

3. What Claude can tell the arm to do

Each request gets one Claude call. Claude returns schema-checked JSON through structured outputs: a list of up to three steps and one sentence. (Opus 5.5 rejects forced tool calls, and structured outputs are simpler anyway.) Claude never sends raw joint targets. Local code checks every step and then turns it into motion.

{
  "steps": [                                   // listed before "say" so steps stream first
    {"do": "gesture", "name": "nod" | "shake" | "shrug" | "wave" | "home" | "ready"},
    {"do": "point",   "target": "A" | "B" | "C"},
    {"do": "jog",     "joint": "base_yaw" | "shoulder" | "elbow" | "wrist_pitch" | "wrist_roll", "degrees": 15},
    {"do": "gripper", "state": "open" | "close"}
  ],
  "say": "one short sentence"                  // shown on screen; optional text-to-speech
}
StepWhat local code doesSafety
gesturePlays a recorded or taught motionFixed motion, capped speed
pointMoves to the taught hover pose above that slotThe scene must be unchanged since the photo
jogReads the current joints, adds the degrees and movesClamped to ±30° per step and to the joint limits
gripperOpens or closes the gripperThe ElRobot follower has one (motor 8). Open and close map to taught values, about 0.65 and 0.36 normalized. Stop squeezing on overcurrent.

After the image, each call also sends a short text context: the current joint angles, which direction is positive for each joint ("base_yaw +: turns left"), the joint limits, and the last three exchanges so that "a bit more" works. Names, directions and limits come from config/arm.yaml (§11).

can't do itShrug

If the request doesn't fit the steps or isn't safe, Claude returns a shrug and says why.

error / timeoutHold

On an API error, a refusal, the 8 s timeout or a failed safety check, the arm stays still and the reason appears in the UI.

stopNever waits for Claude

Typing "stop", a Stop button and a keyboard key all call station_io.stop() immediately, on their own thread.

How targets are marked

Phase 1 uses fixed slots. Three tape outlines on the table each get a taught hover pose, and perception draws a large A, B or C next to each one in the image sent to Claude. Picking a labelled region is very reliable for a vision model, much more so than estimating coordinates.

Phase 2 (stretch) uses numbered marks, so cards can go anywhere. On a plain-coloured mat, OpenCV finds each card's outline and draws a number on it. Claude picks a number. A homography built from four corner markers turns that card's centre into table coordinates. The arm then goes to the nearest pose in a taught 3×3 hover grid, Station has no IK, so the taught grid is the only option. Claude's job stays the same: pick a label.

4. Speed, built in from the start

TechniqueWhat it savesDetail
One call, small outputRemoves repeated round tripsThe answer is a label plus one sentence, about 30 tokens.
Low effortLess thinking timeOpus 5.5 always thinks, so output_config.effort: "low" is the control. Raise it only if accuracy drops on the saved test photos.
Crop and downscaleFewer image tokens to upload and prefillImage tokens are roughly w×h/750. A 768×432 crop is about 440 tokens, against about 1,200 for a 1280×720 frame.
Warm the cache with the current sceneLower time to first tokenWhen the scene has been stable for 0.5 s and differs from the last warmed frame, send a tiny real request with that image (instruction "warm-up", answer ignored). The image block carries cache_control, so the next real request only prefills the new instruction text. This also keeps the HTTPS connection open. It uses a real request because max_tokens: 0 pre-warming is rejected together with structured outputs.
Stream and run each step earlySkips waiting for the rest of the answerAs soon as one step's JSON object is complete in the stream, hand it to the executor. Later steps and say keep arriving while the arm moves.
Ready poseShorter visible waitPointing demos only: when the instruction arrives, start moving to a neutral pose above the middle of the table, so the final move is short. Skip this for free-form commands, where the first step might be a jog.
Reuse one clientAvoids a new TLS handshake each timeCreate a single anthropic.Anthropic() per process.

Optional speed settings to try once everything works: speed="fast" on Opus 5.5 (faster output, 2× price), or a smaller model (Sonnet 5.5, Haiku 5.5) if it stays accurate on the saved test photos. Which model to use is your call. Opus 5.5 is the default here.

Timing log (every run)

Write one JSONL line per instruction with: t_instruction, t_frame, t_sent, t_first_token, t_first_step, t_first_move, t_pose_reached, plus the target, the sentence, token usage (including cache_read_input_tokens) and success. The UI shows the last run as a bar. This log is how you find whatever is slow. No separate benchmark is needed.

5. Code sketch

brain.py

import anthropic, base64, json, re, time

client = anthropic.Anthropic()                 # one client, warm connection
MODEL = "claude-opus-5-5"

JOINTS = ["base_yaw", "shoulder", "elbow", "wrist_pitch", "wrist_roll"]   # ElRobot ids 1,2,4,6,7; rolls 3 and 5 left out

SYSTEM = (
    "You control a small robot arm through a fixed set of steps. The image shows the table, "
    "with regions A, B and C labelled. Turn the user's request into at most 3 steps:\n"
    "- gesture: nod (yes), shake (no), shrug (can't / don't know), wave, home, ready\n"
    "- point: point at region A, B or C\n"
    "- jog: turn one joint by a small number of degrees, using the joint directions given; "
    "never more than 30 per step\n"
    "- gripper: open or close\n"
    "Answer yes/no questions about the table with nod or shake, and point when it helps. "
    "If the request can't be done with these steps, or is unsafe, use a single shrug. "
    "'say' is one short, friendly sentence."
)

def _obj(props):                                   # flat object with every field required
    return {"type": "object", "properties": props,
            "required": list(props), "additionalProperties": False}

STEP = {"anyOf": [
    _obj({"do": {"type": "string", "enum": ["gesture"]},
          "name": {"type": "string", "enum": ["nod", "shake", "shrug", "wave", "home", "ready"]}}),
    _obj({"do": {"type": "string", "enum": ["point"]},
          "target": {"type": "string", "enum": ["A", "B", "C"]}}),
    _obj({"do": {"type": "string", "enum": ["jog"]},
          "joint": {"type": "string", "enum": JOINTS},
          "degrees": {"type": "integer"}}),           # clamped locally to +-30 and joint limits
    _obj({"do": {"type": "string", "enum": ["gripper"]},
          "state": {"type": "string", "enum": ["open", "close"]}}),
]}
SCHEMA = _obj({"steps": {"type": "array", "items": STEP},   # steps before say -> stream first
               "say": {"type": "string"}})
COMMON = dict(
    model=MODEL, system=SYSTEM,
    output_config={"effort": "low", "format": {"type": "json_schema", "schema": SCHEMA}},
    betas=["server-side-fallback-2026-07-01"], fallbacks="default",
)

def _image(jpeg):
    return {"type": "image",
            "source": {"type": "base64", "media_type": "image/jpeg",
                       "data": base64.standard_b64encode(jpeg).decode()},
            "cache_control": {"type": "ephemeral"}}        # cache everything up to the image

def warm(jpeg):
    """Scene settled: cache system + image. Same settings as decide() or the cache won't match."""
    client.beta.messages.create(max_tokens=200, **COMMON, messages=[
        {"role": "user", "content": [_image(jpeg), {"type": "text", "text": "warm-up"}]}])

STEP_RE = re.compile(r"\{[^{}]*\}")      # each step is a flat {...}; the outer object is not

def decide(jpeg, instruction, context, on_step, log):
    """context: joint angles, joint directions and limits, last 3 exchanges - plain text."""
    buf, sent = "", 0
    log["t_sent"] = time.monotonic()
    with client.beta.messages.stream(max_tokens=2000, **COMMON, messages=[
            {"role": "user", "content": [_image(jpeg),
                {"type": "text", "text": f"{context}\n\nUser: {instruction}"}]}]
    ) as stream:
        for text in stream.text_stream:
            log.setdefault("t_first_token", time.monotonic())
            buf += text
            steps = STEP_RE.findall(buf)
            for raw in steps[sent:]:                     # run each step as soon as it closes
                log.setdefault("t_first_step", time.monotonic())
                on_step(raw)                             # executor parses + validates it
            sent = len(steps)
        msg = stream.get_final_message()
    log["usage"] = msg.usage.model_dump()
    if msg.stop_reason != "end_turn":
        return {"steps": [], "say": f"Holding ({msg.stop_reason})."}
    return json.loads(buf)

Check usage.cache_read_input_tokens on the first real request after a warm-up. If it's 0, the prefix differed: compare the image bytes, the system prompt and output_config.

app.py main path

STOP_WORDS = {"stop", "halt", "freeze"}

def handle(text):
    if text.strip().lower().rstrip("!.") in STOP_WORDS:          # never waits for Claude
        station_io.stop(); ui.show({"say": "Stopped."}); return
    log = {"t_instruction": now(), "instruction": text}
    frame = camera.latest();               log["t_frame"] = now()
    jpeg  = perceive.prepare(frame)        # crop + labels + JPEG (same bytes the warm-up used if unchanged)
    context = describe_state(station_io.read_joints(), history[-3:])   # angles, directions, limits, recent turns
    result = run_with_timeout(8.0, brain.decide, jpeg, text, context,
                              on_step=lambda raw: executor.submit(raw, frame, log), log=log)
    if result is TIMEOUT:
        executor.cancel_pending(); result = {"steps": [], "say": "That took too long, so I'm holding still."}
    history.append((text, result)); ui.show(result, log); logs.append(log)

def execute(raw, decision_frame, log):              # executor thread: steps run in order
    step, why = safety.parse_and_check(raw, decision_frame, camera.latest())  # schema, freshness, scene
    if step is None:
        return skills.hold(reason=why)
    log.setdefault("t_first_move", now())
    match step["do"]:
        case "gesture": reached = skills.gesture(step["name"])
        case "point":   reached = skills.point(step["target"])
        case "jog":     reached = skills.jog(step["joint"], safety.clamp_jog(step))   # +-30, limits
        case "gripper": reached = skills.gripper(step["state"])
    log.setdefault("results", []).append({"step": step, "reached": reached, "t": now()})

6. Build plan

M0 · Hardware layer (≈30 min)

Pull the Station calls out of the MCP server into station_io.py. Write smoke.py, which grabs a frame, saves it, prints the joints and moves to home.

Done when: the script runs without errors, and a frame read takes well under a second. If it doesn't, fix the camera first.

M1 · Brain on saved photos (≈45 min, no arm)

Set up three slots with tape. Take about 12 photos of different layouts: shuffled orders, the key missing, and confusing cards such as a padlock, a door and a keyhole. Write the correct answers in bench/frames/labels.csv. Run decide() on every photo.

Done when: at least 11 of 12 are correct at low effort, and the typical response time is acceptable. If not, adjust the prompt or crop, then the effort, in that order.

M2 · Poses + skills + safety (≈45 min)

Teach the home, ready and A/B/C hover poses into poses.yaml. Build point, shake_no and home with a speed cap, joint tolerance and timeout. Test each one with hard-coded targets.

Done when: each skill reaches its pose 5 times in a row, with the e-stop tested.

M3 · End to end in the terminal (≈30 min)

Type a request in the terminal, and the arm runs the steps: gestures, pointing, jogs and the gripper. Add the local stop path and the JSONL timing log.

Done when: the 12-command test set (§0) passes, and the demo beats (§7) work 3 times in a row.

M4 · Speed (≈45 min)

Add the scene-settle warm-up thread, then early dispatch on target, then the ready pose. Check the log after each one and keep it only if the time to first movement improves.

Done when: the log shows cache reads after warm-ups and a steady median time to first movement.

M5 · Demo UI (≈60 min)

Build one page with the live camera view, the image Claude saw (with labels), the target, the say sentence (optionally spoken aloud), and a timing bar for the last run. Add a text box for judges.

Done when: someone who hasn't seen it before can run the demo without help.

M6 · Stretch

Numbered marks for free card placement (§3), multi-step instructions using "targets": [..] with up to 3 items, voice input with push-to-talk and local speech-to-text.

7. Demo script (about 2 minutes)

1 · Understands

The cards are a key, a padlock and a door. "Point to the thing I could use to open a locked door." The arm points at the key. The screen shows Claude's sentence and the timing bar.

2 · Adapts

Shuffle the cards and give the same instruction, and it finds the key in its new slot. Then ask "What keeps a bike safe?" and it points at the padlock. Same cards, different answer.

3 · Declines

Remove the key and repeat the first instruction. The arm shakes "no" and says why.

4 · Judge's turn

A judge types anything they like. Free-form input with a constrained output shows real understanding.

5 · Just talk to it

"Wave hello." "Turn left a little." "A bit more." "Is there anything to eat here?" (it shakes no). "Stop!" The timing bar shows each request going to Claude, then Station, then the arm.

8. Demos that need no camera–arm calibration

Rule: the camera decides what, and taught or recorded poses decide where. Camera–arm calibration is only needed when a pixel has to become an arm coordinate. If every place the arm goes is taught by hand (move the arm there and save the joints), the camera never has to know where the arm is. Recommendation

  1. Main demo: pointing (§7) plus body-language answers. The gestures cost about 20 minutes and make the arm feel like it's communicating, not just moving to positions. The step list in §3 already includes these gestures.
  2. Judge interaction: tic-tac-toe. Turn-based play hides a few seconds of thinking, judges can join in, and it reuses the same one-call brain with the target set to cells 1–9. Check locally that the chosen cell is empty, and if it isn't, ask Claude once more.
  3. If time remains: either the skill picker, if Station's recording or replay is easy to use, or the sticker calibration for free pointing.

Skip any demo that depends on precise grasping of objects at arbitrary positions. Without calibration it's the most likely thing to fail live.

9. Risks and fallbacks

  • Venue Wi-Fi. Use a phone hotspot as backup, and record a video of a good run in case everything else fails.
  • API errors or slowness. The 8 s timeout and any error both lead to a visible hold with the reason shown. The SDK retries 429 and 5xx errors by its default rules, inside the same timeout.
  • Cards shuffled while Claude is deciding. The safety gate compares the slot regions in the decision frame with the live frame and cancels if they differ.
  • Camera bumped. Tape outlines or corner markers are checked at startup, and one key press re-runs calibration.
  • Lighting. Use bold, high-contrast card art, and re-run the saved-photo check under venue lighting.
  • Unsafe motion. The arm only uses taught poses, with a speed cap and joint limits in safety.py, and someone keeps a hand on the e-stop.

11. Arm and Station facts (checked 2026-11-22)

Read from the live arm, the MCP server source and the ElRobot hardware files. The same data is in config/arm.yaml.

Arm

ElRobot follower: 7 arm joints plus a gripper, ST3215 12 V servos, about 430 mm reach. Follower bus 5B8E115950 is the only bus code may command; the leader 5B91043428 is never commanded. Station takes joint-space moves only (no IK). Positions are normalized 0..1 inside each joint's calibrated range; the ST3215 has 4096 steps per turn, and every calibrated range on this arm is centred on step 2048.

  • Hard limits in safety.py: use the URDF limits, which are narrower than the calibrated span on every joint. Assumes step 2048 is the URDF zero; check that once on the arm.
  • Jog cap: ±30° is about 0.15–0.17 normalized on base, shoulder, elbow and wrist pitch, and about 0.09 on wrist roll. The MCP server also clamps any single move to 0.15.
  • Known hazards: shoulder above ~0.9 with a low elbow presses the jaws into the desk; the elbow stalls below ~0.06; a laptop and cables sit right of the base, so keep low moves away from base_yaw < 0.4. Shoulder and elbow sag slightly under gravity.
  • Directions were found by nudging joints and watching the gripper camera, with the wrist upright. Re-check one small jog per joint before the demo.

Cameras and wiring

  • Desk camera (32e6:9228) looks down the table from the far end, 853×480 frames. Gripper camera (32e6:9251) looks between the jaws, 320×240.
  • Working wiring: leader, follower and desk camera each on a laptop port, gripper camera on the extension. That uses the charger port, so the laptop runs on battery.
  • The arm serial adapters don't connect through the extension, and two cameras on the extension exceed its USB bandwidth. Charging means dropping the desk camera, unless Station is patched to cap each camera's bandwidth.
